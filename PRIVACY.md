# Privacy and Personal Data

This document describes how GPT Memory Store handles personal data when deployed as a self-hosted ASP.NET Core REST API. The application persists shared memories for GPT Actions and other API clients in a local JSON file. No data is transmitted to the project maintainers or any external service by default.

## 🔎 What This Document Covers

This document describes how GPT Memory Store at https://github.com/hmlendea/gpt-memory-store handles personal data. It covers the application behaviour and verified integrations described below. Where the software is self-hosted, the instance operator may have separate responsibilities described below.

## 🏠 Self-Hosted Deployments

GPT Memory Store is designed for self-hosted deployment. The instance operator controls the application's configuration, local storage, logs, backups, access controls, retention, and request handling. The project maintainers do not operate a hosted service and do not receive data from self-hosted instances.

The application has no built-in telemetry, update checks, crash reporting, or external authentication integrations that transmit data to the project maintainers or third parties. All data processing occurs within the operator's infrastructure.

## 📥 Data We Handle

### Data Provided to the Application

- Memory records submitted through the REST API: identifier (generated by the application), creation timestamp, optional update timestamp, content (free-text string), source (free-text string), and confidence (decimal value).

### Data Generated or Collected by the Application

- Structured application logs when file output is enabled: operation status, context, and optionally memory identifiers, content, source, confidence, and collection counts. Log output is optional and disabled by default in the provided configuration template.

### Data Received from Integrations

- No personal data is received from integrations or third parties. The application uses local libraries (NuciLog for logging, NuciDAL for data access) that do not transmit data externally.

## 🧭 Processing and Use

The application processes the data described above for these verified functions:
- Create, retrieve, update, and delete memory records — Memory records (identifiers, timestamps, content, source, confidence)
- Return memory collections ordered by revision time then creation time — Memory records
- Record structured lifecycle events for memory operations — Log entries (operation status, context, optionally memory identifiers, content, source, confidence, collection counts)

## 🗄️ Storage, Retention, and Deletion

Memory records are stored in a local JSON file at the path configured by `dataStoreSettings.memoryStorePath` (default `Data/memories.json` relative to the application working directory). The instance operator controls this location, the file's permissions, backups, and durability.

Structured logs are written to the file configured by `nuciLoggerSettings.logFilePath` (default `logfile.log`) when `nuciLoggerSettings.isFileOutputEnabled` is `true`. Log output is optional.

The application assigns a creation timestamp on record creation and an update timestamp on each revision. Records persist until explicitly deleted through the `DELETE /Memories/{id}` endpoint or by direct manipulation of the storage file. No automatic retention or deletion policy is enforced by the application.

For self-hosted deployments, the instance operator controls storage, deletion, and backups for both the memory store and log files.

## 🛡️ Data Protection and Security

- Authentication: All `/Memories` endpoints require a shared API key provided via the `Authorization` header (raw or `Bearer` prefix). The key is configured by the instance operator through `securitySettings.apiKey`.
- Transport: The instance operator is responsible for configuring TLS termination (e.g., via reverse proxy) to protect data in transit.
- Storage: The instance operator controls file-system permissions, encryption at rest, and backup security for the memory store and log files.
- Logs: Structured log context can include memory identifiers, content, source, confidence, and collection counts. Operators should ensure log files are protected equivalently to the memory store when file output is enabled.
- No absolute security is promised; the operator must apply defence-in-depth appropriate to their threat model.
